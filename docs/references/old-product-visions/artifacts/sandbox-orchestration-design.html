1 Core split

The product vision already names a project orchestrator that owns lifecycle, capacity, and monitoring. Decomposition (“planner breaks into subtasks”) is currently folded into that story. For a sandbox orchestration system we split them deliberately.

Planning service · LLM · one-off

  • Triggered by a WorkRun (user intent), not by the tick loop.
  • Reads ingested work items, docs, project goal, persona defaults.
  • Uses inference to decompose, prioritize, attach acceptance criteria, pick worker profiles, declare dependencies.
  • Writes a versioned WorkPlan and exits.
  • May re-run only on explicit replan / reject / policy — never every few seconds.
  • Costly, bursty, non-deterministic → isolated job queue.

Orchestration service · pure logic · continuous

  • Operator loop: every X seconds (plus optional events).
  • Looks for PlanAccepted runs and ready board tasks.
  • Materializes cards, schedules under max agents, spawns/kills workers.
  • Detects stuck sessions, applies timeouts/retries, updates statuses.
  • Syncs mechanical status maps to external boards.
  • Routes HITL blockers — no LLM required for control decisions.

Why this matters: if the reconciler calls an LLM, every tick becomes expensive and non-reproducible. If planning also spawns agents, you cannot audit “what was the plan?” independently of runtime. The durable WorkPlan is the firewall between intelligence and control.

2 Work units

Unit Created by Meaning
WorkRun User / webhook One initiation: “do all open issues on Jira WEB”, “decompose this spec”, “run this ad-hoc task”.
WorkItem Ingest (logic) Normalized raw input (Jira issue, doc section, freeform body) before planning.
WorkPlan Planning service Versioned task graph + policies. Handoff artifact. Immutable once Accepted.
BoardTask Orchestrator materializer Claimable card on the project board. Workers act on these.
WorkerSession Lifecycle manager Runtime process (tmux/container/sandbox) executing one assigned task.

Integration path specifics

  • Org already connected provider credentials; project maps board/project (e.g. Jira WEB).
  • User action: “Run open issues” with a filter (status, label, epic) — or webhook creates a run per new issue / batch window.
  • Ingest stores external keys (WEB-184) on WorkItems; planning may be light (1:1 map issue→task) or heavy (epic decomposition, dependency inference).
  • Orchestration never re-fetches issue text for control decisions; it uses board cards + mechanical status sync.

Document / ad-hoc path specifics

  • No external key initially; planning does full decomposition from goal + docs.
  • Same PlanAccepted handoff — orchestration does not care how the plan was born.

Sandbox note: WorkerSessions should run in isolated sandboxes (containers, VMs, or tightly scoped host sessions). The orchestrator owns sandbox lifecycle the same way it owns process lifecycle: create on assign, destroy on terminal/kill, never leave orphans across ticks.

7 Orchestrator reconcile tick

This is the “operator service” loop: deterministic, idempotent, safe to re-run. Prefer desired state vs observed state reconciliation over fire-and-forget commands. 

flowchart TD
  START([Tick start]) --> LOAD[Load config + capacity]
  LOAD --> PLANS[Find accepted plans needing materialize]
  PLANS --> MAT{New tasks?}
  MAT -->|yes| WRITE[Upsert board cards]
  MAT -->|no| BOARD
  WRITE --> BOARD[Load board + sessions]
  BOARD --> DEPS[Queued → Ready if deps done]
  DEPS --> CAP[Free slots = max − healthy]
  CAP --> SPAWN{Ready + free?}
  SPAWN -->|yes| LIFE[Spawn sandbox workers]
  SPAWN -->|no| HB
  LIFE --> HB[Heartbeats]
  HB --> STUCK{Stuck / timeout?}
  STUCK -->|yes| KILL[Kill · release claim]
  KILL --> RETRY{Retries left?}
  RETRY -->|yes| REQUEUE[Back to Ready]
  RETRY -->|no| FAIL[DoneFailed]
  STUCK -->|no| PROG
  REQUEUE --> PROG
  FAIL --> PROG[Apply worker statuses]
  PROG --> HITL{Blocked?}
  HITL -->|yes| NOTIFY[Notify reviewers]
  HITL -->|no| EXT
  NOTIFY --> EXT[External board sync]
  EXT --> RUN[Roll up WorkRun]
  RUN --> END([Sleep X s])
  END --> START

Source: artifacts/diagrams/orchestrator-reconcile-loop.mmd

  • Idempotent materialize: plan task id → board card id is stable; re-ticks do not duplicate cards.
  • Capacity: never spawn above project max agents; prefer highest-priority Ready tasks with deps satisfied.
  • Stuck definition: no heartbeat for T_stale, or wall-clock > task timeout, or loop budget exceeded (reported by worker).
  • Kill policy: SIGTERM grace → SIGKILL → mark session exited → apply retry policy on the task.
  • Events optional: worker completion can wake the loop early; the periodic tick remains the safety net.

8 Handoff contract

The only object planning must produce for orchestration to proceed: 

WorkPlan {
  plan_id, project_id, run_id, version,
  status: draft | ready | accepted | superseded,
  source: integration | document | adhoc | webhook,
  created_at, accepted_at?,

  tasks: [{
    plan_task_id,           // stable within plan version
    title, summary, spec_md,
    depends_on: [plan_task_id],
    worker_profile,         // coding | copy | triage | …
    acceptance: [criteria],
    priority, estimated_effort?,
    external_ref?: { provider, key },  // e.g. jira:WEB-184
    timeout_s?, max_retries?
  }],

  policy: {
    max_agents_override?,   // optional; else project config
    on_task_fail: leave | fail_run,
    auto_sync_external: bool
  }
}

Once accepted, the plan is immutable. Replanning creates version+1 and marks the old plan superseded. The orchestrator decides how to reconcile in-flight tasks (cancel orphans, keep done tasks, etc.) via pure policy — not another LLM call inside the tick.

9 State checkpoints

CP Name Owner Durable effect
CP1 IntentReceived API WorkRun row; source + filter recorded
CP2 SourcesResolved Ingest logic Raw payloads / doc snapshots stored
CP3 Ingested Ingest logic WorkItems normalized
CP4 PlanningQueued API → plan queue PlanJob enqueued
CP5 PlanDraft Planning service WorkPlan version written
CP6 PlanAccepted API / gate Plan immutable; handoff legal
CP7 OrchestrationOwned Orchestrator Run status → Active; orch is leader
CP8 Materialized Materializer Board cards exist for plan tasks
CP9 Active Reconcile loop Workers scheduled; heartbeats flowing
CP10 RunTerminal Reconcile loop Run completed / failed / cancelled

Checkpoints are crash-recovery anchors: after restart, the orchestrator resumes from the latest durable CP without re-calling the planner unless the run is still in Planning* states.

10 Design decisions & open edges

Decided (for this design)

  • Planning is a job; orchestration is a control loop.
  • Handoff is a durable WorkPlan, not a side-effect of chat.
  • Integration credentials stay at org; runs and fleets stay at project.
  • Fleet-native board remains primary for agents; external boards sync mechanically.
  • Orchestrator may use events for low latency but must reconcile periodically.

Still open

  • Default auto-accept policy per source (webhook 1:1 map vs heavy doc decompose).
  • Mid-flight replan: cancel in-progress vs let them finish under old plan version.
  • Worker unit: tmux session vs container sandbox vs remote VM — same lifecycle API.
  • Whether light integration mapping skips LLM entirely (pure template plan) for cost.
  • Multi-orchestrator leadership if project is multi-instance (lease / single leader).

Next implementation slice: durable schemas for WorkRun / WorkPlan / BoardTask / WorkerSession, a stub planner that emits plans without LLM, and an orchestrator tick that materializes + fake-spawns + reconciles stuck sessions.
