Agent Fleet

A cooperative multi-agent platform for software teams: design workflows with success criteria and guardrails, run many feature workflows in parallel, and let an agent tree grow—and expand—when work is hard or quality fails.

1 Vision & problem

We are building a tool that lets dev teams work cooperatively on projects by spawning up to ~1000 agents, using local and cloud models (via API keys), and running several feature workflows at the same time. Each workflow has its own environment and copy of the worktree; agents in the same workflow share state through SQLite.

Why this exists

One-agent chat does not match how software is delivered. Real work is many features in flight, shared repositories, explicit quality bars, and several people watching the same system. When an agent does a poor job, teams today restart chats or abandon runs. Agent Fleet makes the workflow and the agent tree first-class: you design the path of work, define what “done” means, and the system can rewind and expand the place that failed—without throwing away the whole effort.

Three ideas the product is built around

1

Workflows, not chats

Teams design multi-step workflows with success criteria and guardrails for each step—then run them as versioned recipes.

2

A tree that grows

Each run has an orchestrator that spawns agents. Hard tasks become sub-orchestrators that split work into smaller chunks.

3

Expand on failure

When quality checks prove poor work, stop, expand the blamed node, and re-run only what depended on it—leave the rest intact.

What the team configures

  • Projects — linked to a customer git remote (GitLab or GitHub).
  • Workflows — steps, models preferred per step, and criteria of success.
  • Guardrails — e.g. do not deploy before testing; do not merge to main without a human.
  • Capacity — how many agents and concurrent feature runs the fleet may use.

The UI is web-based because companies often restrict software installs on work PCs. A desktop app is only a later option if we need deeper OS control. A TUI is off the table—it is too limited for this product.

2 Core architecture

So several developers can manage the same agents, the product splits like Temporal into two apps: a Manager (control plane) and Workers (execution plane). Workers can run on infrastructure we provide or be self-hosted by the team. They can install local models when the Manager asks for them. Cloud model calls (Grok, Claude, and similar) are made from the worker, next to the code and tools.

Manager app

Where the team designs, starts, and watches work

  • Create projects and workflows; set success criteria and models.
  • Put guardrails in the workflow (not only in tribal knowledge).
  • Trigger workflows and monitor results—including the live agent tree.
  • Collect human approvals when a run needs a person.
  • Registry of workers; one shared view for the whole team.

Worker app

Where agents actually run

  • Registers with the Manager and pulls new feature runs.
  • Gives each run its own isolated environment (container + disk).
  • Holds the git worktree and the SQLite state agents share.
  • Spawns the orchestrator and the agents under it.
  • Calls local and cloud models; reports progress back to the Manager.

Isolation is per feature run: many agents share one environment, worktree, and SQLite. Other runs do not share that state.

Concurrent features

Several workflows can run at once—each on a different feature, each with its own environment and worktree copy.

Where a run lives

Once a run starts on a worker, it stays there until it finishes. More workers mean more capacity for new runs, not automatic migration of live ones.

The database knows which agent did which task and how the tree nested—so expand targets the right place.

4 What the product does

WF

Workflows with success criteria

Design steps, prefer models per step, and define hard checks for “done”—then publish a version the team can run again.

||

Many features at once

Run several workflows concurrently. Each feature gets its own environment, git worktree, and SQLite shared state.

Tr

Recursive agent tree

An orchestrator spawns agents. If a task is too complex, it can be replaced by a sub-orchestrator that chunks the work.

Ex

Expand on proven poor work

Stop, expand the blamed node, protect good sibling work, and re-run only dependents of the bad outputs.

Gr

Guardrails in the workflow

Do not deploy before tests; do not merge main without human approval; limit what agents are allowed to do.

MW

Manager and Worker split

Multi-developer control plane; workers that run on our cloud or self-hosted; local and cloud models from the worker.

Web

Web Manager

Projects, workflow design, live agent trees, and approval queues—usable without installing a desktop client.

1k

Scale toward ~1000 agents

Capacity comes from many workers and many concurrent runs—not one process trying to hold everything.

5 Agent tree & expand

Each workflow has an orchestrator agent that spawns the others. If an agent realizes its task is too complex, it can request to be replaced by a sub-orchestrator, which splits the task into smaller chunks and spawns agents to do them. That is a recursive nested architecture: the agent tree grows with the complexity of the task.

If it is proven that an agent did a poor job, the workflow stops and goes back to where the poor behavior was detected. The task is handed to a sub-orchestrator that breaks it down more thoroughly. The database keeps track of which agent did each task and the nesting—so the orchestrator knows who is to blame and which node of the tree should expand. After the sub-orchestrator finishes, the parent decides which following work must be re-done and which completed work can stay as-is. 

flowchart TD
  R[Root orchestrator] --> T1[Step: implement]
  R --> T2[Step: open PR]
  T1 --> L0[First agent attempt]
  L0 -.->|criteria failed| SO1[Sub-orchestrator]
  SO1 --> L1[Smaller chunk: schema]
  SO1 --> L2[Smaller chunk: handlers]
  SO1 --> L3[Smaller chunk: tests]
  T2 -.->|waits on implement| T1

The tree grows under the step that needs it. Expand does not force you to rewrite the whole workflow definition.

What expand is for

  • Success criteria failed (proven poor work)
  • Or a human marks work as poor and asks to expand

What expand is not for

  • Config mistakes and policy denials
  • Someone cancelling a run
  • A worker disappearing mid-run

Workflow steps are the spine of a run. Nested agents fill complexity under those steps. That keeps structure predictable for teams—and still allows depth when a feature is hard.

6 How state is kept

Control data and execution data are deliberately separate. The Manager holds what the team needs to design, assign, and observe. Each feature run holds what the agents need to cooperate—on the worker that owns that run.

Concern Where it lives Why
Projects, workflows, users, approvals Manager database (Postgres) Shared multi-developer control plane
Agent tree, who did what, nesting Per-run SQLite on the worker Fast local shared state for agents in one feature
Source code for a feature run Git worktree on the worker Isolated branch per run; push and open MR/PR
Process isolation One environment per run (container) Agents in a run share it; other runs stay separate
Local and cloud models Called from the worker Next to tools and code; keys stay off the browser
Success checks and tools Allowlisted, named checks Criteria are real gates—not free-form shell strings
Human gates Manager approval queue Guardrails like “merge main needs a human” surface to the team
Customer repositories GitLab or GitHub Project points at the remote the team already uses

A run’s durability lives with the worker that owns it. Adding workers increases how many features you can start—not how many live runs automatically fail over.

8 Stack & boundaries

These choices support the product shape above. They are implementation stance for v1, not the vision itself—but they make the vision concrete.

Manager API · Rust Worker · Rust Manager Web · Vite + React Postgres · team data SQLite · per-run data OpenAPI contracts Containers per run TUI · out of scope
  • Rust for Manager API and Worker—concurrency, process control, shared types.
  • Web SPA for the Manager so corporate browsers are enough.
  • Contracts between UI, Manager, and Worker so multi-dev and multi-worker stay coherent.
  • Models: worker initiates local and cloud inference; Manager does not need to proxy every call.

v1 product focus

Software-team feature workflows: implement → verify against success criteria → open merge request or pull request—with multi-developer Manager oversight.

Out of scope for early product

  • TUI or a rich terminal product as the main surface.
  • Desktop packaging (possible later if OS control becomes necessary).
  • Moving a live feature run to another worker mid-flight.
  • One container or process per agent (agents in a run share an environment on purpose).
  • Unrestricted shell as the default way to define success or run tools.

9 Success picture

A day when the product is working looks like this—not “agents that never need people,” but high parallel throughput with clear quality and low team toil.

  1. The team creates a project linked to GitLab or GitHub and invites members.
  2. They design a workflow: steps, success criteria, models, and guardrails—then publish it.
  3. They start several runs for different features. Each gets its own worktree, environment, and SQLite state.
  4. Orchestrators grow agent trees. Agents implement, run success checks, and open MRs or PRs.
  5. When criteria prove poor work, the system expands the blamed node and re-runs only what depended on it.
  6. People use the web Manager to watch trees, answer approvals, and enforce merge or deploy gates—without installing a local control app.

Success is cooperative scale (many agents, many features), explicit quality (criteria + expand), and team-safe control (Manager / Worker, guardrails, web UI).

10 Open questions

Settled for this vision

  • Cloud models are called from the worker (alongside local models).
  • Web is the product surface; TUI is out.
  • Manager / Worker split is required for multi-developer use.
  • Per-run isolation (environment + worktree + SQLite) is foundational.
  • Customer git may be GitLab or GitHub.

Still open

  • How aggressive should automatic “request a sub-orchestrator” be versus steps the team designed by hand?
  • Default expand depth and cost budgets before the system stops or asks a human?
  • When—if ever—should a desktop worker host be offered for deeper OS control?
  • Later: restore a paused run on another machine, or always start a fresh run?
  • How far multi-organization tenancy goes beyond a single-team deployment?
